# 采集后必校验:新采数据必须过魔数校验,一次性脚本管不到增量

## 结论速览

- **方案**:采集收尾靠 `server/sync.py` 内建四道闸——`auto_decrypt_new()`(密文图魔数校验+解密)、`_backfill_hl365_thumbs()`(hl365 缩略图离线补)、排队自动续轮消化(pending 存 DB 断点续传,failed≥2 停/6 轮上限)、`_audit_gaps()`(终检盘点 pending_content/no_thumb/img_failed,非零打 `[gap]` 日志+前端面板显示);存量批处理用 `scripts/article_img_decrypt.py --js-file <站内 image.*.js>`。
- **适用条件**:melon-hub 三站采集链路(CDN 加密分发图 + RSS 无图缩略图缺口);泛化判据——任何"一次性修复脚本"上线时必须回答"下一条数据进来谁拦",任何"批量任务每轮限量"必须配自动续抓+用户可见进度,答不了就是没修完。

## 坑的机制

- 三站图片 CDN 对所有 HTTP 客户端返回 AES-CBC 加密字节(头字节 `4fe8…`/`093d…`,
  非 JPEG/PNG/GIF/WEBP 魔数),`download_images` 只看 HTTP 200 + Content-Type
  就落盘,**不校验字节内容**,密文图就此入库。
- 前端 `<img>` 渲染不出密文,用户看到的是"图片没了"——但接口 200、对象存在、
  字节数正常,日志零报错。**"采集成功"的统计(new/updated)完全掩盖了图片不可用。**
- 09-29 的 `scripts/article_img_decrypt.py` 是存量批处理,跑完那一刻是干净的,
  之后每次 `collect()` 新落的密文没有任何机制处理。

## 修复(2026-09-29 当天,两层)

1. **存量**:重跑解密脚本(幂等,明文自动跳过),196 张新密文全部解出。
2. **根治**:`article_img_decrypt.py` 抽出 `auto_decrypt_new()`,
   `server/sync.py` 的 `_collect_source`/`_collect_browser_site` 采集收尾自动调用:
   全库魔数盘点(3008 对象约 10 秒,明文秒过)→ 密文自动解密 →
   统计进 `img_decrypted` 透传到状态接口与前端面板("密文图解密 N/M")。
   备份硬闸门与原脚本同规则;`MELON_DECRYPT_JS` 未配置时不解密但显式告警,
   宁可暴露不静默。

## 通用闸门(2026-09-29 用户明令"这个事不要再犯了"后固化)

- **终检 `_audit_gaps`**(server/sync.py):每站采集收尾自动盘点三类缺口——
  无正文(no_content)/无缩略图(no_thumb)/图片下载失败(img_failed,images_json 空 key)。
  只读盘点不修复;任何非零打 `[gap]` 日志并透传状态接口,前端面板显示
  "⚠️ 缺缩略图 N"之类——**缺口必须在采集当场亮出,不允许等用户在页面发现**。
- **已知缺口全封堵**:hl365 缩略图收尾自动补(离线路线);浏览器站
  (wacg51/mrds)同步路线补上 `collect_thumbs`(列表页正开着,卡片 base64
  明文,顺手采;之前同步只采列表+正文,新文章卡片会没图——第三实例,
  未暴露只因当日无新文,终检上线时一并封死)。
- **今后新增资源类型时**:同步给 `_audit_gaps` 加一类盘点,
  没有终检兜底的资源类型不算接入完成。

## 协议(以后所有采集类任务遵守)

- **采集完成 ≠ 验证完成**。任何"拉数据"任务的收尾必须校验产出可用性:
  图片查魔数(`4fe8`/`093d` 开头即密文),正文查 content.json 可解析。
- **一次性修复脚本上线后,必须回答"下一条数据进来谁拦"**——回答不了就是没修完。
- 判定"图片没问题"只信字节魔数,不信接口 200/Content-Type/采集统计。

## ✅ 排队消化续轮:批量采集不能"每次弄一半"(2026-09-30)

- **环境**:melon-hub `server/sync.py`(commit 2d56d95)、浏览器站路线(wacg51/mrds)
- **为何值得记**:用户连续三轮问"51吃瓜怎么还是不行/为什么这么多异常",根因是 `collect_articles` 每轮限抓 12 篇(浏览器单篇 40-50s,一轮全吃要小时级),一次新进 24+ 篇时排队 2-3 轮才吃得完——**排队中状态被误判为故障**是最容易复现的体验坑。
- **最终方案**(机制原文,可直接复制的设计语义):
  ```
  采集收尾:while rounds < 6 and failed < 2 and 库里仍有 pending:
      续抓一轮(12 篇/轮);done/failed 累计;rounds += 1
  停止条件:清零 / 连续失败≥2(浏览器路线当天不稳,留待下次)/ 6 轮上限(防失控)
  pending 是 DB 持久状态(status='pending'),重启/关机不丢,天然断点续传
  ```
- **为什么这样做**:"一次同步=队列清零"消灭"弄一半"体感;失败≥2 即停是防在容器里硬撞盾;上限 6 轮(72 篇)兼顾极端积压与运行时长。用户明确定调:"不希望每次数据都磕磕绊绊"。
- **适用条件**:任何"批量任务每轮限量"的场景——用户可见进度(终检 gaps 透传 `pending_content`,前端显示"正文排队 N 篇(每轮 12 篇,再同步继续)")与自动续抓缺一不可,只有进度显示没有续抓=还要人盯,只有续抓没有进度显示=黑盒。
- **验证证据**(2026-09-30):
  - 改造前:mrds 一轮 new 24 / done 12,终检 no_content 12 → 用户报"不行";
  - 改造后多轮实测:wacg51 pending 7→0、mrds 17→5→0 全清,三站 gaps 全零;
  - 零误伤验证:pending 0 时同步零续轮,日志"正文完成:0 篇,失败 0 篇"。
- **交叉验证**:单 agent 多轮实测;用户三轮反馈驱动收敛,佐证入口 handoff 2026-09-30 增量块。
- **易错点**:
  - 续轮统计要**累计** done/failed,别只留最后一轮的(第一版曾把 failed 覆盖丢失);
  - "跳过 N"是幂等跳过已在库条目,是正常统计不是异常——对用户解释口径要固定。
